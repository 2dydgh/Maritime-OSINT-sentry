# 사건별 AI 조사

제안 탭에서 **사건 검토 → AI로 현재 상태 확인**을 누르면 Pydantic AI 에이전트가 선택한 선박 쌍의 관측과 온톨로지 근거를 확인합니다. 추가 CPA 계산이나 시나리오 비교의 필요성과 호출 순서는 모델이 선택합니다. 첫 버전의 최종 조치 선택지는 서버 규칙으로 제한됩니다.

## 사용 흐름

1. 제안 또는 판단·실행 기록의 사건 카드에서 **사건 검토**를 엽니다.
2. **AI로 현재 상태 확인**을 누릅니다. 실행한 확인 작업과 원본 결과를 볼 수 있습니다.
3. 권장 조치, 서버가 다시 확인한 사실, 참고한 근거, 확인할 점을 검토합니다.
4. 필요할 때 **속력·침로 조건 비교**를 엽니다. 조건 비교하기 → 최소 거리와 주변 영향 확인 → 선택적으로 검토 이유 저장 → 사건 검토로 돌아가기 순서입니다. 같은 조사로 돌아오면 작성하던 판단 이유가 유지됩니다. 비교 중 승인 유효 시간이 지났다면 최신 상태를 다시 조사합니다.
5. 집중 추적 제안이면 이유를 입력해 승인하거나 기각합니다. 승인 시 기존 승인 API가 현재 위험을 다시 확인하고, 브라우저가 추적 실행 여부를 보고합니다.
6. 승인 후에는 **승인 후 상태 확인**에서 관측과 추적 기록을 확인합니다. 제안 카드의 주 동작도 승인 후 상태 확인으로 바뀝니다.
7. 조사 기록은 창을 닫아도 유지됩니다. **조사 취소**는 별도 동작입니다. 취소·실패·시간 초과 시 기존 확인 기록이 남습니다.

화면에 표시하는 것은 실제 도구 호출·완료 기록이며 모델의 내부 사고 과정이 아닙니다. 최종 설명은 모델이 선택한 조치·사유 코드가 검증된 뒤 서버 문장으로 표시합니다. 거리·시각은 원본 분석값에서 가져옵니다. 자유 서술 전체를 자동으로 사실 검증한다고 주장하지 않습니다.

## 구현

- `backend/services/investigation_agent.py`: Pydantic AI 도구 선택 루프, 도구 어댑터, 근거·조건 검증
- `backend/services/investigation_store.py`: 기존 WATCH_DB의 `investigations` 테이블, 실행 중복 방지·복구
- `backend/routers/investigations.py`: 시작·조회·취소 API
- `static/js/investigation.js`, `static/css/investigation.css`: 조사·근거·승인 화면

도구: `inspect_current`, `query_knowledge`, `recalculate_cpa`, `compare_scenario`.

- 도구 인자는 현재 사건으로 제한됩니다. 임의 SQL·URL·파일·다른 사건 ID를 모델에 허용하지 않습니다.
- 온톨로지는 기존 RDF/OWL·SHACL·고정 SPARQL을 사용합니다. 완전한 조회 결과를 보존하고 모델에는 축약해서 전달합니다.
- CPA 도구는 기존 CPA 함수를 호출합니다. 충돌 ML 모델을 재실행하거나 교체하지 않습니다.
- 시나리오는 한 선박의 속력 -20% 또는 방향 ±15도, 15분 비교, 사건 조사당 최대 2회입니다. 기존 엔진에 선회 60초·속력 변화 120초를 적용합니다. 해안·수심·항법규칙 등을 고려한 최적 운항안은 아닙니다.
- 시나리오 생성 자체는 운용자의 검토·채택으로 기록하지 않습니다. 저장된 비교는 기존 화면으로 재생할 수 있습니다.
- 승인·기각·추적 실행은 에이전트 도구에 없습니다.

## 검증과 기록

모델은 조치 코드·사유 코드·실제 근거 ID를 제출합니다. 서버는 근거 소속, 현재 상태·관측 유효성, 온톨로지 검증 결과, 조치 조건을 대조합니다. 상태가 바뀌면 모델에 재확인을 요청하고, 재시도 한도 안에 해결하지 못하면 실패로 남깁니다. 결과 게시 직전에도 검사합니다.

SHACL 위반은 추가 검토로, 관측·분석 지연은 갱신 확인으로, 기존 승인·추적은 중복 제안 없이 상태 확인으로 연결합니다. 검증 통과는 관측·충돌 모델·운용 판단 정확도의 보증이 아닙니다.

조사 결과를 이용한 승인에는 `investigation_id`를 전달합니다. 60초 이내의 검증된 집중 추적 결과만 허용하며, 기존 승인 시 CPA 검사도 다시 수행합니다. 같은 DB 트랜잭션에 조사 결과·근거 스냅샷과 운용자 판단을 함께 보존합니다. 온톨로지에는 `Decision → usesInvestigation → AgentInvestigation`으로 연결됩니다. 나중의 재조사가 승인 당시 근거를 바꾸지 않습니다.

## 실행 한도·운영 범위

- 사건당 진행 중 조사 1건, 전체 동시 조사 최대 2건
- 조사 전체 180초, 모델 요청 최대 8회, 도구 실행 최대 10회, 총 토큰 최대 24,000
- 재시작 시 종료된 프로세스의 미완료 조사는 중단으로 복구합니다. 자동 이어하기는 없습니다.
- 현재는 단일 호스트 로컬 사용을 전제로 합니다. 사용자 인증·역할 권한·다중 호스트 분산 실행은 별도 범위입니다.
- 실행 기록에는 모델명과 근거·조치 검사 결과가 남습니다. 별도 메시지 전송이나 선박 조종 연결은 없습니다.
- WATCH_DB 백업에 조사 기록이 포함됩니다. 시나리오 DB도 함께 백업해야 비교를 재생할 수 있습니다.

## 모델 설정

`uv sync --inexact --locked`로 의존성을 설치합니다. `pydantic-ai-slim[openai]` 1.x를 사용하며 실제 버전은 `uv.lock`에 고정합니다.

- `OLLAMA_BASE_URL`: 기존 Ollama 주소, 기본 `http://localhost:11434`
- `INVESTIGATION_MODEL`: 조사 전용 모델명. 미설정 시 기존 `OLLAMA_MODEL` 사용

도구 호출을 지원하는 모델이 필요합니다. 모델 설치 여부 확인만으로 품질이 검증되지는 않으며 실제 사건 도구 호출·제안 검증까지 시험해야 합니다. 모델이 없거나 응답하지 않으면 성공한 조사로 대체하지 않고 실패·시간 초과를 표시합니다.

컨텍스트를 제한한 로컬 설정 예시:

```text
FROM qwen3.5:9b
PARAMETER num_ctx 8192
PARAMETER num_predict 800
```

위 내용을 Modelfile로 저장한 뒤 `ollama create maritime-investigator:9b -f Modelfile`로 기존 가중치를 재사용하는 모델 설정을 생성할 수 있습니다. `.env`에 `INVESTIGATION_MODEL=maritime-investigator:9b`를 지정하고 백엔드를 재시작합니다. GPU 사용 여부는 Ollama 배포 환경에 따르며 이 기능이 GPU 설정을 변경하지 않습니다.

## API

- `POST /api/v1/investigations/proposals/{pid}`: 시작 또는 이미 진행 중인 조사 반환
- `GET /api/v1/investigations/proposals/{pid}`: 최근 10개 조사
- `GET /api/v1/investigations/{rid}`: 진행·결과·저장된 근거
- `POST /api/v1/investigations/{rid}/cancel`: 취소
- 기존 `POST /api/v1/proposals/{pid}/decision`: 선택적으로 `investigation_id` 전달

## 사용 흐름 보완 (2026-09-15)

- 조사 화면은 **조사 당시 결론 → 다음 행동 → 근거 → 실행 이력** 순서로 표시합니다. 상단에는 현재 사건 상태를 별도로 표시합니다.
- 근거 버튼은 수신 시각·분석값·누락된 정보 등을 요약해 보여주며 JSON은 **원본 데이터 보기**에 접어 둡니다. 저장된 시나리오 근거에서는 비교를 재생할 수 있습니다.
- 실행 이력의 시작·완료는 작업별로 묶되, AI가 반복 확인한 작업은 별도로 남깁니다.
- 승인·기각 후 다시 열어도 서버의 현재 사건 상태를 읽어 중복 판단 버튼을 표시하지 않습니다. 해당 조사로 내린 판단인지도 표시합니다.
- 승인 후 **이후 관측·추적 상태 확인**으로 기존 후속 관측 화면에 바로 연결됩니다.
- 60초가 지나면 집중 추적 승인은 다시 조사가 필요합니다. 기각은 사건이 검토 대기이고 검증된 집중 추적 제안인 경우 과거 근거를 참고해 기록할 수 있습니다.
- 새 조사나 다른 이력을 선택하면 이전 근거 표시를 초기화합니다. 주기적 상태 갱신은 운용자의 입력 오류 메시지를 지우지 않습니다.
- API 응답의 `case`는 조회 당시 사건 상태·판단 요약·버튼 표시 정보입니다. 저장된 조사 원본과 승인 당시 근거를 변경하지 않으며, 최종 승인 권한 검사는 기존 서버 트랜잭션에서 다시 수행합니다.

검증: 관련 Python 검사 66개, JavaScript 검사 15개 통과. 격리 브라우저에서 근거 요약·모바일·승인·재열기·후속 확인·취소·이력 분리를 확인했으며 JavaScript 오류가 없었습니다. 모델과 조사 도구 선택 로직은 변경하지 않았습니다.

## 반복 확인 후 호출 한도에 도달하는 문제 수정 (2026-09-15)

실제 HAI QIN–YAU KEE 28 조사에서 `UsageLimitExceeded`가 발생했습니다. 저장된 확인은 `open/정상 → expired/analysis_stale → expired/vessel_stale`로 바뀌었습니다. 기존 검증은 상태 또는 지연 사유의 문자열만 바뀌어도 재확인을 요구했습니다. 이전 실행에는 개별 출력 거절 이유가 저장되지 않아 모델의 마지막 출력 내용은 복원하지 않습니다.

- 같은 **관측 갱신 확인** 조치에 해당하는 분석 지연·관측 지연·자료 누락은 최종 서버 재확인에서 같은 대응 범주로 취급합니다. 최종 현재 자료는 별도로 다시 읽고 보존합니다.
- 집중 추적을 제안할 때의 근거 유효 시간·현재 위험 검사·운용자 승인 요건은 유지합니다. 실제 필요한 조치가 달라지면 서버가 새 근거 ID와 수정할 조치 정보를 모델에 반환합니다.
- 온톨로지 근거와 자료 부족·처리 완료 등 상태를 확인했으면 추가 조사 도구를 닫고 모델이 최종 결과를 제출하도록 합니다. 서버가 AI의 최종 결과를 대신 만들어 성공 처리하지 않습니다.
- 실패 이유를 호출 한도·제안 검증 실패·모델 연결 실패 등으로 구분합니다. 이전 실패 기록도 조회 시 명확한 문구로 표시하며 저장 원본은 바꾸지 않습니다.
- 새 실행부터 제안 검증 거절 이유를 `validate_rejected` 확인 기록으로 남깁니다.

관련 Python 검사 70개와 JavaScript 검사 15개 통과. 지연 사유와 제안 상태가 바뀌는 재현, 보수적 안내의 정상 종료, 실제 조치 변화의 재검증, 과거 실패 메시지 개선을 포함합니다.

동일 사건을 12081번 실제 서버에서 다시 조사해 20초 만에 완료했습니다. 도구 호출 2회(현재 상태·온톨로지 근거 조회) 후 관측·분석 갱신 확인을 제안했고 서버 검증을 통과했습니다. 승인·추적은 실행하지 않았습니다.
